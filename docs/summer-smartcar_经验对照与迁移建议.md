## 2. 先建立两辆车的对应关系

| 控制层 | summer-smartcar | McarPVC | 可以借鉴的内容 |
| --- | --- | --- | --- |
| 图像输入 | 摄像头新帧触发视觉处理 | 摄像头新帧触发视觉处理 | 边界、中线、偏差和特殊赛道处理的分层 |
| 视觉转向 | 像素偏差生成舵机角度 | 像素偏差生成车体角速度 `omega` | P、非线性 P、差分 D、陀螺阻尼的思想 |
| 前进速度规划 | 偏差大时降低基础速度 | 偏差大时降低 `vx` | 减速及时、加速平滑、出弯再判断 |
| 轮速分配 | 舵机角度参与左右轮差速分配 | `vx、vy、omega` 经逆运动学分配四轮速度 | 将车体决策和执行器控制分开 |
| 速度反馈 | 两个编码器、两个速度 PID | 设计为四个编码器、四个速度 PID | 目标、实测、输出一起观察 |
| 调参 | IPS200 菜单、参数实体、历史 VOFA | 当前 printf 到 UART1，VOFA 观察 | 参数可追溯、每次修改有记录 |

旧车的左右轮差速配合舵机转弯；麦轮车的四轮差速本身承担转向和横移。某一轮速度跟不上，在旧车上主要影响驱动力和左右协调；在麦轮车上还会改变合成的前进、横移和自转分量。因此，四轮速度反馈和轮序、符号核对更关键。

当前 `ENCODER_ENABLE=0`、`WIFI_SPI_ENABLE=0`。四轮 PID 尚未参与实际闭环，轮速目标目前乘 `MOTOR_OPEN_LOOP_GAIN=0.10` 映射为占空比，并限制在 ±20%。VOFA 中的 `Actual=0` 表示反馈不可用。当前设定的 120/80 cm/s 是控制指令，不是已测得的车速。

## 3. README 与现存源码有几处重要差别

1. **旧项目的 VOFA 发送当前被注释。** README 介绍了 20 通道发送和非阻塞图传，但现存 `main.c` 中常规遥测、停车事件遥测、`vofa_uart_poll()` 和 `debug_image_poll()` 调用均被注释。模块存在，不等于当前主循环正在调用。
2. **旧源码已有出弯加速门控。** `exit_accel_allow`、`exit_stable()` 和相关计数逻辑已经存在，PID 还用它限制前馈。这部分不能只依据 README 的旧摘要判断。
3. **独立 100 Hz 陀螺采样属于历史计划。** 当前旧源码仍在视觉更新调用链中执行 `gyro_read_update()`；TIM7 做按键扫描。不能把 README 的计划当成已实现的中断。
4. **旧停车阈值的单位需要核对。** `control_stop_poll()` 直接比较 `encoder_get_left_speed()/right_speed()` 的 ±10，而这两个 getter 返回的是采样周期脉冲数。它不是直接比较滤波后的 cm/s；README 的“10 cm/s”表述不能照搬为标定值。
5. **配置宏不一定是运行时生效值。** McarPVC 的 `CAR_SPEED_MAX_CMS/MIN_CMS` 仍为 220/160，但当前速度规划使用 `ctl_speed_straight/curve`，初值是 120/80。配置里保留的菜单说明也不代表当前存在菜单调用。

源码：[旧主循环](../../../summer-smartcar/summer-smartcar/smartcar/user/src/main.c:151)、[旧出弯门控](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:264)、[旧停车判断](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:141)、[旧编码器接口](../../../summer-smartcar/summer-smartcar/smartcar/code/encoder/encoder.c:32)。

## 4. 经验一：先确定是哪一层出问题，再调 PID

旧 README 早期记录过视觉耗时达到 37～54 ms、目标速度未达到预期、外轮输出饱和等现象。它随后记录了优化后视觉耗时约 13～18 ms 的结果。这里最值得继承的是诊断顺序，而非这些耗时数值。

在 McarPVC 上建议依次回答：

1. 摄像头是否持续产生完整新帧？主循环是否及时消费？
2. 二值图、真实边界、补线、中线和有效行是否合理？
3. `g_vis.err` 是否连续、方向是否正确？陀螺反馈是否抵消旋转？
4. `vx、vy、omega` 是否符合当前轨迹需求？
5. 四轮 `Target` 的轮序和符号是否正确？
6. 编码器到货后，四轮 `Actual` 是否分别跟上？
7. 各轮输出是否饱和，电源、驱动、接线、负载是否限制执行？

例如：图像误差跳变与轮速跟踪差，分别属于不同层。提高速度环 Kp 无法修复错误补线；提高转向增益也无法修复某一轮编码器方向反了。

另外，`Out` 很大而 `Actual` 很低，只能说明输出大而编码器轮速没有跟上。它可能涉及电源、负载、堵转、驱动或反馈标定，不能单凭这两条曲线断言“轮胎空转”。判断滑移还需要视频、实测距离和时间等车体运动证据。

参考：[旧 README 调试记录](../../../summer-smartcar/summer-smartcar/README.md:429)。

## 5. 经验二：控制周期必须看实际执行时间与调用位置

旧车速度环在 TIM6 每 5 ms 运行，按键扫描在 TIM7 每 10 ms 运行，视觉与转向外环跟随摄像头新帧，约 20 ms。旧车左右轮差速分配也在速度中断中更新。McarPVC 则在每次视觉外环更新后计算四轮目标，5 ms 中断执行轮速控制和 IMU 更新。

50 Hz 外环、200 Hz 内环可以作为当前设计起点，但“配置为这个频率”不能代替实测。需要观察完整主循环负担，包括视觉、printf、未来图传，以及中断执行时间；平均耗时低于 20 ms，也不代表最慢帧不会超时。

两套视觉转向都使用 `e[k]-e[k-1]` 作为 D 项，没有显式除以实际帧间隔。帧率或漏帧改变时，同一 D 增益的效果也会改变。这是今后解释抖动时必须考虑的条件。

RT1064 性能提高有利于留出处理余量，但图像处理阻塞、旧图像反复驱动、串口传输和状态机依赖新帧的问题，仍需分别处理。当前 McarPVC 缺少持续无新帧时的运行超时保护；建议作为后续独立修改项，本次没有实现。

源码：[旧 TIM6/TIM7](../../../summer-smartcar/summer-smartcar/smartcar/user/src/isr.c:115)、[当前 PIT 处理](../project/user/src/isr.c:28)、[当前外环](../code/control/control.c:342)。

## 6. 经验三：前瞻距离要结合图像坐标和相机安装实测

旧 README 曾纠正一次前瞻方向理解：图像第 0 行在远端，第 119 行在近端。因此，采样行号减小才是在图像上看得更远。旧车曾尝试更远的采样位置后回退，说明提前看弯和偏差可靠性之间需要实车取舍。

旧 `calc_adaptive_far()` 对误差和采样位置各做一次 0.35 平滑，以减少前瞻窗口来回跳动。默认基准行 55，三个区间的目标偏移是 −5、+3、+5；窗口变化和误差计算本身存在反馈关系，需要看实际采样行曲线。

McarPVC 有对应函数，但 `#if ADAPT_PREVIEW_ENABLE` 出现在宏定义之前；按当前源码顺序，不能因后面写了 `#define ... 1` 就认为前面的条件分支开启。旧项目通过顶部 `config.h` 提前定义，当前移植版本没有保留相同的定义顺序。这是本次阅读发现的待修复项，没有修改源码。

即使以后修复宏位置，也不能直接认定旧车的 55 行适合新车。相机高度、俯仰、镜头、车头到摄像头距离改变，都会改变“55 行”对应的实际地面距离。应按已有硬件验证方案记录近、中、远位置与地面距离，再选择前瞻窗口。

源码：[旧动态前瞻实现](../../../summer-smartcar/summer-smartcar/smartcar/code/vision/vision.c:891)、[旧前瞻配置](../../../summer-smartcar/summer-smartcar/smartcar/user/inc/config.h:17)、[当前前瞻条件编译](../code/vision/vision.c:903)。

## 7. 经验四：出弯加速不仅看偏差，还要看车身是否稳定

旧 `motor_speed_calc()` 根据偏差规划速度，并把减速和加速分开处理。更进一步，源码通过 `was_corner`、`exit_settle_frames`、`exit_hold_frames` 和 `exit_accel_allow` 管理出弯过程：

- 大偏差或大舵角时记录进入弯道，禁止快速放行。
- 出弯后，同时检查陀螺角速度、舵角和视觉偏差；连续稳定若干帧才允许较快加速。
- 未稳定时仍以较小系数加速，并关闭额外前馈，而不是完全冻结速度。
- 设有等待帧数上限；持续满足入弯条件又会重置计数，不能简单将其理解为所有情况下固定 0.5 s 后放行。

当前 McarPVC 对所有加速使用 0.05，对减速使用 1.0；`CAR_ACCEL_ALPHA_FAST=0.15` 暂未用于这条运行链，也没有旧车的出弯稳定门控。

可借鉴“车身稳定后再加速”的结构，但麦轮没有舵角反馈。未来应结合视觉偏差、真实陀螺角速度、角速度指令和轮速跟踪情况重新定义稳定条件。旧车的 2.5° 舵角阈值不能换个变量名就拿来与 deg/s 比较。

源码：[旧稳定判据和加速模式](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:264)、[旧速度规划](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:337)、[当前速度平滑](../code/control/control.c:389)。

## 8. 经验五：同名 PID 和 FF 参数，不代表控制律相同

两套速度 PID 都采用增量形式，核心关系是：

`Δu = Kp·(e[k]−e[k−1]) + Ki·e[k] + Kd·(e[k]−2e[k−1]+e[k−2])`。

但额外输出部分不同：

| 项目 | 现存实现 |
| --- | --- |
| 旧车 | 满足正向欠速及出弯放行条件时，`ff = Kff × Target`，再与累积输出相加 |
| McarPVC | 满足正向欠速条件时，增加 `Kff × (Target−Actual)` |

所以，同样的 `FF=0.10` 不能视为已经继承同样的前馈效果。旧车在条件满足时按目标给补偿，当前版本按误差给额外补偿；两者对误差变化的响应不同，并且都存在条件门控。

旧 README 记录了 FF 增大后过冲、回退的经历，也提出过进一步降低增益、关闭 FF 等计划。应借鉴分开测试 PID 和额外补偿的方式，不能把计划里的参数当成已验证结论。

四个新电机的驱动、电压、负载、编码器换算可能不同。当前左侧 Kp=1.0、右侧 Kp=1.2 等值可以作为待验证初值；不能凭旧车左右两轮的表现判断新车四轮已调好。编码器未到时，也不能用 `Actual=0` 的曲线做闭环调参。

源码：[旧 PID 与前馈](../../../summer-smartcar/summer-smartcar/smartcar/code/pid/pid.c:24)、[当前 PID](../code/pid/pid.c:49)、[当前四轮 PID 参数](../code/config/config.h:182)。

## 9. 经验六：舵机角度不能直接当成麦轮角速度

旧 `servo_calc()` 的视觉控制量含 P、二次 P、差分 D 和陀螺阻尼，之后还乘 `14/35`，限制为 ±14°，再加舵机中位角。其输出是舵机角度，35 是该实现中的经验缩放常数。

当前 `omega_calc()` 直接输出 deg/s，并限制到 ±120 deg/s。同样的像素偏差，即使公式外观相近，两套参数的单位和作用也不同。旧车转弯还依赖行驶速度、轴距和舵机机构；麦轮自转取决于四轮合成的转动分量。

旧 `motor_inject_ackermann()` 用舵角、几何比例和增益生成左右轮不对称差速，含 outer/inner 经验系数。McarPVC 的实际分配是：

```text
rot = omega(deg/s) × π/180 × (L+W)/2(m) × 100
FL  = vx − vy − rot
FR  = vx + vy + rot
RL  = vx + vy − rot
RR  = vx − vy + rot
```

这组公式使用车轮中心间的完整纵向距离 L、横向距离 W。当前暂用 L=15 cm、W=16 cm；这是待实测的临时值，不是旧车给出的数据。旧车的 Ackermann 增益、舵机中位和左右轮权重没有直接对应的麦轮参数。

今后若四轮目标超过执行能力，需要考虑共同缩放能否保持所需速度比例；单轮分别截断可能改变实际合成运动。当前临时模式确实逐轮限幅到 ±20%，因此还要观察是否有轮子先饱和，以及整数占空比取整是否吞掉较小的差速指令。

源码：[旧舵机控制](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:211)、[旧左右轮分配](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:460)、[当前角速度控制](../code/control/control.c:237)、[当前逆运动学](../code/motor/motor.c:124)。

## 10. 经验七：起步、闭环切换和停车要单独验证

旧车在 5 ms 速度控制函数内判断开环起步退出，条件是左右轮各自达到阈值，或者超时；起步期间还把 PID 累积输出和实际开环占空比保持一致，并在转换后限制输出增量。

McarPVC 当前编码器分支的起步退出判据在视觉外环中，以 FL 与 RR 的平均速度判断。这不是四轮分别达标；其开环输出也没有同步写入每轮 PID 的累积输出。切换后到下一次正常视觉更新之间，还需检查目标是否及时生成。这些是以后启用编码器前的检查项，不能照抄旧车 40% 起步、180 cm/s 退出就默认切换平顺。

停车同样不能机械复制。旧车主要向前行驶，负输出常用于制动；现存旧源码已经关闭“停车时裁掉正输出”的开关。麦轮横移、后退、自转时允许某些轮速为负，这些轮子可能需要正向输出来制动。

当前 McarPVC 的编码器停车分支仍设置 `Speed_PID_StopBrake=1`，PID 会裁掉正输出。因此需要按各轮速度方向分析制动，而不是把“正向输出”统一视为发车输出。当前无编码器分支直接归零停机，此问题属于恢复闭环前的待处理事项。

另一个可借鉴点是让停车推进与相机新帧解耦。旧车在主循环每轮都执行 `control_stop_poll()`；当前编码器停车推进仍在外环状态分支中，计数超时也依赖帧到来。若相机停帧，按帧计数的超时不能代替独立时钟超时。

源码：[旧起步/切换](../../../summer-smartcar/summer-smartcar/smartcar/code/pid/pid.c:97)、[当前起步外环](../code/control/control.c:364)、[当前开环执行](../code/pid/pid.c:160)、[当前停车](../code/control/control.c:170)、[正输出裁剪](../code/pid/pid.c:96)。

## 11. 经验八：视觉保护要看原始证据和时间连续性

旧 README 曾遇到连通滤波后底部图像异常，最终利用停车原因确定是 LOST 而非斑马线。将原始底部图像用于出界检测，可以避免把处理算法产生的伪影当作直接场景证据；同时保留处理后的图像，才能定位是拍摄还是算法出了问题。

斑马线确认次数也要结合速度和帧率。旧记录出现过斑马线只在少数帧满足条件，确认次数偏大导致漏停。但单次确认更容易受单帧误检影响，必须与多行一致性、位置、赛道结构一起验证，不能认定“改成 1 就普遍正确”。

旧车也曾试加固定距离门槛，后来因赛道位置不符回退。经验是先确认起点、斑马线和特殊赛道布局，再设计上下文门控。当前没有编码器，尤其不能假装具有已标定的行驶距离。

当前移植视觉还需继续审查：无有效前瞻行时旧误差是否继续使用、没有十字候选的帧是否推进状态退出、补线索引是否覆盖边界。这些风险不能因旧车曾完赛而自动消失。应复用已有审查结论，并在真正修改时用对应输入图像验证。

源码：[旧发车与视觉顺序](../../../summer-smartcar/summer-smartcar/smartcar/user/src/main.c:105)、[当前新帧处理](../project/user/src/main.c:147)、[视觉审查记录](控制链条逐函数审查.md)。

## 12. 经验九：遥测和图像上传必须保留完整、对应的数据

旧 VOFA 模块把待发数据放入 TX 环形缓冲区，由 UART6 发送中断逐字节搬运，避免主循环一直等待串口。这里是发送队列，与当前逐飞库用于接收电脑字节的调试 RX FIFO 方向不同：一个等待发出，一个保存收到的数据。

这套模块也有需要注意的条件：缓冲大小 128 字节、有效容量 127 字节，发送请求过长或剩余空间不足时返回 `false`。调用方没有统计发送失败，日志中少一帧便可能难以区分是采集没有发生还是发送被丢弃。当前旧主循环又关闭了发送调用，不能仅凭模块存在判断日志完整。

若以后把非阻塞发送思想应用于 RT1064，应根据每行字节数、发送频率和波特率计算预算，并记录丢帧数；重新使用 RT1064 的 UART/DMA 接口，不能复制 MM32 的 UART6 寄存器操作。115200、8N1 的理论有效字节率约为 11520 B/s，还应给突发消息和处理延迟留余量。是否需要替换当前 printf，应依据实测阻塞时间决定。

旧 README 还记录了上传过程中图像被新帧改写，导致花屏，解决思路是在发送前保存图像和边界快照。McarPVC 的 WiFi 源码已经有图像复制缓冲区，暂时被模块开关关闭。今后恢复上传时，应继续核对图像和边界是否来自同一帧，以及复制时摄像头 DMA 是否正在改写原图。单纯关闭 CPU 中断不能保证 DMA 停止写内存。

旧 README 的停车日志缺失教训也值得保留：不能只在发车标志为真时记录，否则停车动作一清标志，最重要的制动段就消失了。未来日志应包含运行、事件触发和停车后短时段，而不是只看正常循迹。

源码：[旧 TX 缓冲与发送](../../../summer-smartcar/summer-smartcar/smartcar/code/vofa/vofa_uart.c:74)、[旧图像快照](../../../summer-smartcar/summer-smartcar/smartcar/code/vofa/vofa_uart.c:156)、[当前遥测](../code/control/control.c:437)、[当前 WiFi 快照](../code/wifi/wifi.c:154)。

## 13. 经验十：按键事件、状态切换和参数发布要考虑中断竞争

旧 TIM7 在有待消费短按事件时暂停扫描，以避免下一次扫描把短按状态覆盖为 RELEASE。这说明“10 ms 扫描按键、主循环执行动作”的分工，需要额外解决事件保存问题。

但旧做法会因一个按键待消费而暂停所有按键扫描，不能直接作为新车的最终实现。更合适的候选方案是每个按键单独锁存事件或使用事件队列，并明确长按是否只触发一次、按住期间是否重复。当前 McarPVC 仍直接周期扫描，这属于后续检查项。

旧发车与停车还用短临界区同步修改 PID、中间状态和运行标志，避免速度中断读到一半更新的状态。McarPVC 在主循环逐个写四轮目标时，同样要考虑中断读取到新旧目标混合的可能性。未来可先计算完整目标快照，再用短临界区统一发布；不能把整段视觉、SPI 图传或 printf 包在关中断区域里。

源码：[旧按键事件保护](../../../summer-smartcar/summer-smartcar/smartcar/user/src/isr.c:142)、[旧发车临界区](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:80)、[当前四轮目标发布](../code/control/control.c:410)、[当前按键扫描](../project/user/src/isr.c:42)。

## 14. 参数迁移边界：哪些要重新测，哪些只能作为初值

| 参数或方法 | 对 McarPVC 的处理原则 |
| --- | --- |
| 旧编码器 `ENC_TO_CMS=1.117` | 绑定旧编码器与 5 ms 周期，不直接复制；新车逐轮核对方向并标定脉冲/米 |
| 当前脉冲/米初值 2000 | 是待标定初值，不是已测量结果 |
| L=15 cm、W=16 cm | 暂时保留，按轮中心距离实测；见硬件验证方案 |
| 旧轴距、舵机中位、最大舵角、Ackermann 权重 | 属于旧舵机车机构，不移植为麦轮几何参数 |
| 前瞻行 55 与动态偏移 | 结合新相机姿态、图像、地面距离重新验证 |
| 旧 P、P²、D、陀螺阻尼系数 | 控制输出单位改变，不能按数值相同认定效果相同 |
| 左右轮 Kp 差异 | 新车四轮分别验证；旧右轮表现不能代表新 FR/RR |
| `FF=0.10` | 先明确是目标前馈还是误差补偿，再独立测试 |
| 40% 起步、180 cm/s 退出、1 s 超时 | 是旧车策略参数，须先解决新车切换逻辑并低风险验证 |
| 旧陀螺死区、20 deg/s 量化、±500 限幅 | 与旧传感器和噪声条件相关；不直接复制到当前 SPI IMU |
| 停车阈值 ±10 | 先核对原代码的脉冲单位，不能按 README 描述当作 cm/s |
| 旧完赛时间和平均轮速 | 只作为历史经验；轨迹、滑移、距离和电压变化都影响用时 |

源码：[旧轮速换算](../../../summer-smartcar/summer-smartcar/smartcar/user/src/isr.c:120)、[旧陀螺处理](../../../summer-smartcar/summer-smartcar/smartcar/code/control/control.c:518)、[当前轮速标定初值](../code/encoder/encoder.c:38)。

旧 README 中一次按目标圈速比例提高参数后效果不佳，是很有用的反例。圈速不会随 PWM、Kp 或目标速度按相同比例变化；更高的编码器平均轮速也不保证车体沿更短、更稳定的轨迹完赛。

## 15. 后续工作顺序建议：仅作为计划

### 15.1 编码器未到阶段

先使用现有临时模式，按 [硬件模块验证方案](硬件模块验证方案.md) 核对四轮轮序、正方向、辊子布局、前进/横移/自转符号、摄像头姿态和 IMU 正方向。保持清楚：此阶段能观察方向和视觉纠偏，但无法验证四轮真实速度跟踪。

软件侧优先关注按键事件保存、无图像超时、有效视觉结果判定、动态前瞻宏顺序和已有补线边界问题。当前主循环已经有初始化失败后禁止进入正常运行、停止电机的门控，应保留这个改进；无需再将它列作“完全缺失”的功能。

### 15.2 编码器到货阶段

逐轮校准符号与脉冲/米，确认低速测量分辨率，再验证四个单轮速度环。之后检查起步向闭环切换、目标快照发布、全方向制动与超时退出；这些通过后才评估整车速度和视觉参数。

### 15.3 基础循迹稳定后

依次评估动态前瞻、出弯稳定门控、目标比例保持、非阻塞遥测和在线改参。横移增益当前为 0，未来增加横移会改变视觉偏差、车体运动和制动需求，应单独作为一个实验变量。

源码：[当前初始化失败门控](../project/user/src/main.c:119)。本节没有授权或实施任何固件改动，后续需要另行按实际任务执行。

## 16. 继承旧 README 的实验记录方式

旧项目最适合长期继承的是可追溯的调试记录：写清修改前后、数据、车体现象和回退，而不是只留下“这一版感觉更快”。建议每次上车使用下列模板：

| 项目 | 要记录的内容 |
| --- | --- |
| 版本 | 代码版本、未提交改动、编译配置、开关状态 |
| 条件 | 电池电压、地面、轮胎、赛道、相机位置、负载 |
| 参数 | 本次实际生效值，以及相对上次改变的唯一主要变量 |
| 数据 | 帧编号/时间、视觉耗时和有效性、err、gyro、vx/vy/omega、四轮 Target/Actual/OutCmd、停车原因 |
| 观察 | 直道、入弯、弯中、出弯、特殊赛道、停车分别描述 |
| 结果 | 哪个现象改善或恶化，是否输出饱和，是否出现丢帧/日志丢失 |
| 决定 | 保留或回退，依据是什么，下一轮要验证什么 |

现有 20 通道容纳不下所有建议诊断量；可按实验切换诊断通道组或另记事件，避免在不了解带宽的情况下盲目增加打印量。无编码器时应明确标记反馈不可用，不将占位 0 记成真实轮速。

本次吸收的主要经验是：保留分层控制，先定位证据所在层；按实测数据理解时序和单位；用旧车的调试方法指导新车，用新车自己的硬件数据决定参数。
