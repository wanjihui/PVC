## 本轮控制修改

仅把 `code/config/config.h` 的 `CTL_LATERAL_GAIN_DEFAULT` 从0改为**0.10 (cm/s)/px**，上位机现有键为 `lateral_gain`。gyro_kd=0.30、视觉1.60/0.012/0.30、四轮Kp=0.20/0.20/0.18/0.18、Ki=0.001、Kd=0、150cm/s和500ms保持。

`control_update()` 每个新图像缓存：

```c
vy = abs(err) < deadband ? 0 : -err * lateral_gain;
```

横移与视觉转向共用2px死区，避免贴近中心时持续微调。err>0表示赛道在右侧，vy<0代表向右横移。偏差20/50/100px分别对应2/5/10cm/s横移；无需添加弯道分类或更改固定前瞻。

5ms任务仍将前进、横移和陀螺阻尼后的转向一起分配：

```text
rot = 19cm × omega(deg/s) × pi/180
FL = vx - vy - rot
FR = vx + vy + rot
RL = vx + vy - rot
RR = vx - vy + rot
```

例如vx=150、omega=0、err=+50，vy=−5：四轮目标155/145/145/155cm/s。这里改的是目标轮速，四个独立速度PID再计算占空比，未直接对PWM增加固定补偿。

横移使小车能同时修正位置和转向，但不会独立测量或锁定车头相对赛道的航向。单个视觉偏差可能同时来自位置偏移和车头偏斜。如果贴线改善但车头仍歪，不能继续无限提高横移增益来代替航向纠偏。

下轮先保持0.10。如横移方向正确、回线仍慢，再试0.15，每次增加0.05；若左右蛇行、出弯反向过冲或轮速误差变大，先减到0.05，必要时0关闭。以上是试调步长，不是已验证的最优增益。可导入 `调参方案_20261009_横移010.json`；导入不自动发送，在线应用以匹配车辆回执为准。

22:18:03.468，配套日志明确记录第1次 `STOP reason=2`（丢线）。此后仍收到176个停车参数包，一直到第2次发车。当前app_poll的IMU参数、图像、日志不受K1/K2门控，停车不会停止通信。

第2次最后22:18:23.201仍有vx=150、PWM=24/7/11/14%、vision_event=0，后面CSV和JSONL同时没有数据，文字日志也没有STOP。上位机直到22:39:08才停止监听。最后几个包视觉耗时约1.35～1.39ms、周期约19.6ms、WiFi服务耗时0～55us，累计峰值1.784ms。没有断流前逐渐阻塞的迹象，但不能排除最后一包之后发生主循环卡住、SPI故障或模块/网络异常。没有后续样本不能等同于车实际停车，也不能据此确认无线信号已断开。

## 查到的确定通信缺陷与修订

旧版 `network_ready` 只由初始化/重连结果赋值。异步事务失败后，wifi.c只退避1s，app.c仍认为网络已连接，因而 `!network_ready` 的停车重连分支永远进不去。另外，空RX轮询成功也清除上传错误，可能把“SPI能读，但上传仍失败”误报成恢复。

本轮修订：

1. 连续3个事务失败后，WiFi层报告本地通信不可用；成功的空RX不清上传失败累计，完整发送成功才清除。
2. 应用层通过 `wifi_is_ready()` 读取故障状态；故障后至少5s且车辆已停车，才调用原有同步初始化重新入网。行驶中仍保持非阻塞服务，K2立即清PWM。网络故障本身不自动发车，也不增加停车策略。
3. 未发出的日志保留，旧参数和半帧图像丢弃，重连后发送最新数据并补发错误/停车日志。阈值、退避、重连等待在config.h集中配置。
4. 每3s缓存一条 `[NET] ms=... state=... stop=... vis=... data=... images=... errors=...`。它不做同步UART打印，也不在ISR发送。state=2运行，0停车；data/images是本地成功提交的参数包/完整图像计数，errors为累计事务失败数。`WIFI_STATUS_PERIOD_MS=0`可关闭。SPI成功不等于电脑确认收到UDP。

这修复了明确的故障恢复缺口，**尚不能证明它是本次断流的唯一根因**。如果模块无线链路异常但SPI一直接受数据，UDP没有接收确认，固件无法靠本地OK识别；如果主循环完全停止，也不能靠主循环重连。下轮需同时记录断流时K2能否停车、三路接收是否一起停，并保存日志；若再次无线全断且无错误日志，可临时接串口读取已有错误输出。没有复现证据前，不认定是WiFi模块固件或硬件问题。
