后续版本提示：本说明记录的是当日增加弯道在线调参之前的源码快照。晚间默认前瞻已改60，弯道13项也加入运行参数，在线共36项；控制分层与PID公式保持，详见[晚间分析与修改](前瞻60_单边中线与出弯斜行分析_20261013.md)。下文默认45/23项描述属于该快照。

核对日期：2026-10-13。依据当前工作目录中的实际源码，解释正常循迹分支；不是对已烧入芯片版本或实车效果的确认。本次只增加说明文档，没有修改控制代码、参数或桌面程序。

普通工程与 `rt1064_single_udp.uvprojx` 默认单端口；`rt1064_curve_legacy.uvprojx` 通过编译宏切换旧三端口。两者使用相同视觉、速度规划、运动学和电机控制源码。

## 1. 先区分各层的量

| 层级 | 当前变量 | 含义与单位 |
|---|---|---|
| 图像 | `vision_gray[120][188]` | 一帧原始灰度，像素0～255 |
| 二值图 | `Image_Used` | 黑0、白255 |
| 边界 | `g_vis.l_border/r_border` | 每一行边界列号，255无效 |
| 中线 | `g_vis.center_line` | 每一行期望行驶位置的列号 |
| 视觉偏差 | `g_vis.err` | 相对画面中心94的加权偏差；缺行时可能经放大，不总是纯像素几何距离 |
| 视觉转向需求 | `vision_omega_command` | deg/s，尚未叠加陀螺阻尼，尚未最终限幅 |
| 车体前进目标 | `speed_target_dbg` | `vx`，cm/s，经过起步和弯道规划 |
| 车体横移目标 | `vy_dbg` | `vy`，cm/s，正值向左 |
| 车体转向目标 | `omega_dbg` | `omega`，deg/s，正值车头左转 |
| 四轮目标 | `Motor_PID[i].Target` | FL、FR、RL、RR各轮线速度，cm/s |
| 四轮测量 | `Motor_PID[i].Actual` | 编码器计算的轮周线速度，cm/s |
| 控制器累计输出 | `Motor_PID[i].Out` | 浮点占空比百分数 |
| 待下发输出 | `Motor_PID[i].OutCmd` | 浮点占空比；当前无附加项，所以等于Out |
| 实际写入电机 | `(int16)OutCmd` | 整数占空比百分数，符号决定方向 |

视觉误差不直接送四个速度PID。运动学先把整车需求转成四轮目标，然后各轮PID只比较自己的目标和实际轮速。编码器测到轮子转动，不能直接证明轮子没有打滑；IMU角速度也没有测出整车横移速度。

## 2. 入口、初始化、运行状态和调度

`project/user/src/main.c` 只有 `app_init()` 和无限重复的 `app_poll()`。

当前 `config.h`：`APP_DRIVE_ENABLE=1`，`APP_VISION_TRACKING_ENABLE=1`，`APP_IMU_VERIFY_ENABLE=0`，`ENCODER_CLOSED_LOOP_ENABLE=1`，`CTL_CURVE_SPEED_ENABLE=1`。

因此 `app.c` 的上半段正常入口参与编译，下半段“主循环只验证IMU”入口不运行。没有舵机控制，没有40%固定占空比起步，没有180cm/s后才切闭环的阶段。状态只有 `CAR_IDLE=0` 与 `CAR_RUNNING=2`。

`app_init()` 实際顺序：

1. 系统时钟600MHz、调试串口初始化；电机DIR/PWM初始化，PWM为0。
2. 恢复全局中断，等待300ms，记录启动日志。此时PIT还没有初始化。
3. IMU初始化与静止校准，保存 `imu_ready`。
4. 编码器初始化；其接口返回void，日志CONFIGURED表示已调用，不能证明外部编码器工作正常。
5. 摄像头最多尝试初始化3次；失败重试之间等待200ms；保存 `camera_ready`，初始化视觉微秒计时器。
6. `control_init()` 清四轮PID、状态、命令、里程、十字/斑马线等历史，打开停车时的陀螺零偏跟踪，再清PWM。
7. 初始化按键。`drive_allowed = APP_DRIVE_ENABLE && imu_ready && camera_ready`。
8. `sensors_ready=1`，启用PIT_CH0每5ms；允许发车时再启用PIT_CH1每10ms。
9. 初始化WiFi、记录成功/失败与READY，网络正常则请求补发缓存的启动日志。

WiFi初始化失败不直接剥夺已经通过的电机控制资格；当前发车资格依赖IMU/相机。IMU失败时5ms任务仍采编码器，但跳过IMU更新且不运行控制/PID；相机失败同样禁止发车。

| 路径 | 周期/触发 | 实际任务 |
|---|---|---|
| CSI中断 | 相机完成帧 | SDK回调更新完成缓冲指针并置finish标志 |
| 主循环视觉 | 有新帧才执行 | 快照、图像处理、事件决策、更新视觉命令 |
| PIT_CH0 | 5ms，200Hz | 编码器→IMU→车体命令/运动学→四轮PID/PWM |
| PIT_CH1 | 10ms，100Hz | 扫按键、锁存K1、直接执行K2停车 |
| 主循环WiFi | 每圈分步推进 | 参数/日志/图像异步发送、接收在线参数 |
| 参数生成 | 50ms | 最新参数包，20Hz生成目标 |
| 图像上传启动 | 最少66ms且有新图 | 约15fps上传启动目标，实际完成帧率取决于链路 |
| PWM载波 | 17kHz | 硬件产生驱动波形，并非PID计算频率 |

摄像头配置50fps，视觉若能及时消费则约20ms更新一次，不能把配置帧率当成必达的实测处理频率。PIT的5ms调用也依赖中断能及时执行，没有硬实时测量就不能断言绝无迟到。

`app_tick_isr()` 顺序不能理解反：先采本拍实际，再产生本拍目标，随后PID使用两者计算PWM。两张图之间，视觉缓存保持，但陀螺阻尼、速度规划、四轮反馈仍每5ms更新。

`app_poll()` 顺序：`app_buttons_poll()` → `app_vision_poll()` → 停车时必要的网络重连 → `wifi_poll()`生成数据/图像候选 → `wifi_poll_log()`推进异步事务及接收命令 → 主循环延时。当前 `APP_MAIN_LOOP_DELAY_MS=0`。

### K1与K2

逐飞 `KEY_LIST={C15,C14,C13,C12}`，因此K1=C15、K2=C14；上拉输入，低电平按下。库短按事件在松手后生成；应用把事件锁存，避免主循环忙时被下一次扫描覆盖。

K1短按松开→`buttons_scan_isr()`保存START→主循环 `buttons_poll()`→`control_state_launch()`。只有IDLE接受发车；清PID累计输出与误差历史、清视觉D项、清起步与弯道状态、清里程、关闭运动时零偏跟踪；进入RUNNING，缓存一次当前视觉需求，最后 `Speed_PID_Enable=1`。第一拍5ms中断开始输出，不是上电自动发车。

视觉reset清十字/斑马线/路宽等状态，但不清 `g_vis.err` 和整张边界数组；K1入口的首次 `control_update()`可能先使用停车期间最近一次处理结果，之后由新图像更新。

K2累计按下20ms时扫描中断直接调用 `control_state_stop()`；已识别的释放/长按事件也有停车路径。停车优先清待处理K1，按住K2不能发车。主循环再次消费STOP是确认，不是唯一停车机会。

停车关PID、清四轮目标/历史/输出、PWM归零、清vx/vy/omega及弯道缓存、记录reason、进入IDLE，恢复停车零偏跟踪。清PWM不等于机械瞬间零速度，也没有额外主动制动阶段；下一拍Actual仍可能显示惯性余速。K2不关闭摄像头/IMU/日志传输。

共享 `PIT_IRQHandler()` 先处理CH0，再处理CH1；CH2/3仅有清标志代码，目前未用于控制。CSI仅处理采集回调；UART1接收进调试FIFO，不是速度环入口；UART6接收函数为预留代码，当前WiFi参数不经UART6。

## 3. 摄像头新帧怎样成为稳定输入

逐飞库 `mt9v03x_finished_callback()` 在两个CSI图像缓冲间更新 `mt9v03x_image`，置 `mt9v03x_finish_flag=1`。中断里不做Otsu、搜线、PID或WiFi发送。

`vision_capture_frame()` 仅短暂屏蔽CSI中断，在finish置位时清标志，将188×120原始灰度复制到 `vision_gray`；恢复CSI。PIT仍可运行。没有新帧返回0，主循环不重复对旧图像做视觉D项。

`vision_gray` 同时作为本次算法和上传画面来源。算法处理的是二值化副本 `Image_Used`，上传保留灰度。WiFi开始上传时再复制到独立 `monitor_image`，后续视觉帧不会覆盖在途图像。完成标志不是无界帧队列，主循环落后时不能假设每个相机帧都逐一处理。

## 4. vis_deal逐步处理

`vision.c:2003` 的实际顺序是：Otsu阈值缓存→二值化→原始二值图出界预检→连通滤波→斑马线检测/事件生成→清本帧边界→逐行扫边→十字检测/补线→中线与偏差→导出轨迹/统计耗时。

### 4.1 Otsu和二值化

`compute_otsu()` 每隔4行4列统计灰度直方图。遍历0～255候选阈值，比较黑白两类的类间方差，取最大值，阈值限制20～235。

`vis_deal()` 每10个已处理帧重算一次；阈值以 `0.3*新值+0.7*旧值` 平滑。首次有效计算前使用128；计数从0递增，因此前9帧是128。随后每个像素 `gray>threshold` 为白255，否则黑0。reset没有重置函数内部static阈值缓存。

### 4.2 原图出界检查

`out_of_bounds_check()` 在连通滤波前查看 y=100～119，使用上一帧底部真实边界向两侧扩大3列；边界无效时保持最近有效窗口。默认窗口约47～141。白像素总数<40报告本帧LOST，并记录全黑行数。

这一层在滤波前检查，是因为滤波由底行白像素传播，底行黑可能擦掉上方白；不能把这种滤波结果误当作整个底部区域本来就没有赛道。

### 4.3 连通滤波

`filter_bottom_connected()` 底行所有白点作为连通种子，自118行向上处理到10行。

每行：复制下方连通标记→左到右，允许下方同列/±1/±2列或本行左侧连通→右到左补本行右侧连通链→将仍不连通的白点擦黑。这是在每行近似传播赛道连通性，不是完整全图BFS。与底部连通的环境白仍可能保留；不能保证所有杂物都滤掉。

### 4.4 斑马线事件

`zebra_detect()` 用上一帧真实底边界±3列的窗口，对119、114、109三行调用 `zebra_row_scan()`。每个列点先经±2列多数表决；行宽不足30不检查。

有效行须同时满足：白占比25%～75%、黑白跳变≥10、宽度≥4的黑段≥5、白段≥5。至少两行有效，还需条纹跳变位置在±3列内达到60%对齐；三行有效时至少两对对齐。

当前连续确认为1帧，漏检最多保持2帧。单行有效只预确认，不会单独产生检测结果；相关注释里“要凑2帧确认”是旧值解释。

`zebra_prev` 将持续检测转换成上升沿事件。检测/保持斑马线时不报LOST；未检测斑马线且raw_oob成立才报LOST。视觉层仍继续搜线，不直接停车。

## 5. sweep_boundaries逐行搜边和丢线处理

主要函数 `vision.c:492`。

### 5.1 种子与底行

`longest_white_col()` 在列47～141间每5列采样，统计从119行往上的连续白高度，取最长列作为seed。它不是“选整行最大白面积”。

底行从seed向左右扩展，遇到连续两个黑像素才停；找出的宽度<3返回扫线失败。贴画面边缘的坐标不算真实边界。扫线保存边界坐标、exist标记，以及不经过外推的raw数组。

### 5.2 向上跟随

从118扫到5行，左起点是上一行左边界+8，右起点是上一行右边界-8；起点不白则回seed。继续向外到“白→连续两个黑点”。双边真实且左<右时更新路宽，限制20～160。

普通丢右边：用 `真实左边+last_valid_width` 维持下一行搜索；丢左边反之。裁剪的外推坐标没有真实exist标记。

双边都丢：中心采样列也全黑时累积黑行，连续5行便把更远区域设INVALID并停止扫线；存在白时当作白区候选，不按普通黑区丢线处理。

扫线返回失败不直接等于应用停车；应用LOST依据前面的raw_oob事件。

### 5.3 正入十字候选

连续≥3行双边丢但中心有白，远侧行号≥31时记录near/far候选。离开白区也可提交候选；白区伸到31行以外的远处取消，抑制普通弯道误判。

确认白区后从seed重新找双边，暂时禁止普通单边外推；直到双边真实恢复。raw数组持续记录原始扫线，避免把外推当真实拐点。

### 5.4 当前斜入候选状态机

`CROSS_USE_OBLIQUE_SWEEP=1`，所以当前运行扫线内的斜入辅助；旧 `cross_get_ref_center/cross_detect_oblique` 位于反向编译条件中，不参与本版。

连续单边丢≥7行启动有角侧下拐点查找。首次检查已经扫过的区域，随后每行仅检查新的 `y+3` 候选；有角侧触发后固定，防止中途左右互换。

辅助函数：

- `cross_edge_l/r()` 读取本帧raw真实边界；丢线用-12/200哨兵，避免读取当前尚未写回的g_vis。
- `cross_oblique_dn_at()` 需要候选下方4行趋势稳定，相邻变化≤10；上方3行已经真实扫到并形成方向正确的至少1、2、2像素变化。
- `cross_find_oblique_dn()` 找第一个满足条件的近侧点。
- `cross_oblique_up_tear()` 比较当前行与已扫过下方3行的1、2、2像素方向变化，生成上拐点候选。
- `cross_oblique_up_stable()` 至少再向上扫3行，看远侧变化是否稳定≤10。
- `cross_oblique_lost_side_continuous()` 上下点之间丢线侧若出现>10行真实边界则否决，抑制普通弯道误判。

上拐点搜索期间左墙有角从列168重新扫，右墙有角从列20重新扫。找到上下点后将该段受污染边界设INVALID，交给补线；扫到y=5仍找不到上点时，用屏幕顶部角兜底（左墙有角用187,0；右墙有角用0,0）。兜底点不是实测拐点。

## 6. cross_detect与cross_repair怎样影响实际控制

正入优先：下点从near+5向下找双边真实的首行，最多到115；找不到用底角 `(0,119)/(187,119)`。上点从far-3向上最多找20行稳定锚点，至少行5；相隔3行左右变化均≤8为稳定。`cross_corner_has_band_gap()` 检查两点间有INVALID或≥6像素跳变；底角snap跳过断带检查。

正入不成立且扫线斜入有效时，采用有角侧上下点；丢失一侧的拐点显示值清INVALID。有角侧方向另存，短暂漏检保持时不会被每帧重置的斜入变量破坏。

状态NONE→CANDIDATE→DETECTED，需要连续2个有效图像。首帧候选可以显示拐点，但 `cross_repair()` 只有DETECTED且点有效才补线。确认后最多保持4个漏检帧，约80ms（若50Hz处理）；再漏就清状态、坐标和补线模式。

`cross_fill_segment()` 是按指定两端点的直线插值：

```c
k = (c1-c0)/(r1-r0);
c(r) = k*r+b;
```

必须r1>r0且坐标合法；包含两端，端点强制原值，列限制0～187。补线设exist=1，并用独立repair_flags标注左右来源。因此exist并不总表示真实像素边缘。

正入桥接左右各自上下点；斜入桥接有角侧真实点，丢线侧补为x=0或187、从顶部到近侧拐点行。后面的 `pho_center()` 使用补线重算中线，紫线不是单纯显示装饰，会影响err和电机。

注意：补线插值经过端点，但随后 `pho_center()` 还会做3点平滑，显示/最终用于中线的边界可能受到这一步微调。

## 7. pho_center中线、前瞻、权重与缺行放大

`vision.c:940`。

先对边界执行 `border_smooth()`：y=1～118的三个合法列号做平均，拟议变化>8像素就跳过；这是原地平滑，下一行会读取部分已平滑值，不是独立输出数组。

逐行从近到远生成中线：

1. 双边真实或显式十字补线有效：`center=(left+right)/2`。只有没有repair标记且双边真实才更新 `last_real_width`，限制20～160。
2. 只有左真实：`center=left+last_real_width/2`；只有右真实：`center=right-last_real_width/2`。先按未裁剪宽度推中线，再限0～187，避免用假屏幕边缘取平均。
3. 两边都无效：取本行滤波后白像素横向重心；白点<3则中线255无效。
4. 中线再执行3点平滑。

普通单边内部搜索外推不算十字补线，不向上位机画紫线；但可信单边仍可外推中线并参与纠偏。

`asc_far` 限制20～100作为取值中心，取中心±10；默认45取y=35～55，含端点21行。y小看得远，y大看得近。这是像素行，不是车前45cm。

从近行55向远行35累积，权重每行增加0.2，近端1、远端5：

```c
total_dev += (center_line[y]-94)*w;
g_vis.err = total_dev/total_w;
```

合法中线可参与；只有无边界白重心时排除两侧3像素附近亮点，真实/补线支持的0/187仍参与。

重要实现细节：`theo_rows=y_near-y_far` 当前等于20，虽然循环含21行；有效行<20时乘 `min(20/valid_cnt,2.5)`。例如只有8行，平均+40会输出+100。因此CSV err超过94不必然是越界值，可能是这个放大。完全无有效行则保留上一帧err，不自动归零。

元数据记录本帧真正用到的far/near；上位机绿线随下一完整图像同步变化，暂停显示时画面与该帧标记一起保持。

## 8. control_update：err变转向和横移

`control.c:311` 在短临界区执行；停车清视觉命令后返回。运行时调用 `omega_calc()`，将当前误差缓存为两个车体指令。

```c
if (e < ctl_deadband && e > -ctl_deadband) e=0;
delta=e-err_last;
err_last=e;
vision_omega_command = CONTROL_IMAGE_TURN_SIGN *
    (ctl_omega_kp1*e + ctl_omega_kp2*e*abs(e) + ctl_omega_kd*delta);
vision_vy_command = in_deadband ? 0 : CONTROL_IMAGE_TURN_SIGN*g_vis.err*ctl_lateral_gain;
```

默认死区严格在(-2,+2)，恰好±2会参与。`CONTROL_IMAGE_TURN_SIGN=-1`：赛道在右、err正，右转omega负、右横移vy负；左侧反之。

视觉控制为线性P+二次P+每帧差分D，没有视觉积分项。

- kp1=1.60：普通偏差强度，e=40产生64deg/s。
- kp2=0.012：e=40产生19.2deg/s，e=80产生76.8deg/s；所有非零e都参与，不是某阈值后开关。
- kd=0.30：误差从30变40，产生3deg/s；误差下降时提供相反的变化项。
- D没除实际帧间隔，它是像素/帧差分；改变视觉帧率会改变同样时间变化下的D作用，不能当成固定dt的连续微分。
- 横移gain=0.10，e=40→vy=-4cm/s。它没有独立横移PID，没有横移速度测量反馈，也没独立vy限幅；四轮闭环仅跟踪合成轮速目标。

`control_update()` 同时把未叠加陀螺、未最终限幅的视觉转向需求交给弯道判断；本函数不直接写PWM。

## 9. 起步和弯道速度规划

控制中断先推进 `ramp_elapsed_ms`，再读最新控制角速度并调用 `curve_speed_tick()`。

默认 `ctl_speed_target=150cm/s` 是直道上限，不是四轮永远目标150。起步包络为：

```c
launch_limit = ctl_speed_target*ramp_elapsed_ms/ctl_ramp_ms;
```

500ms升到150，每5ms上升1.5cm/s；这是前进速度目标，不是占空比。没有最低固定起步占空比。起步从首拍就保留转向、横移、陀螺和四轮PID；若转向需求非零，个别轮目标可以很快非零甚至反转。

每个新帧 `curve_update_frame()` 按 `abs(vision_omega_command)` 选级：<70直道、70～<140普通弯、≥140紧弯。升到某一档需同档连续2帧；超过100ms的帧间隔会清待确认。已进入的等级只升级，紧弯不在弯中反复退到普通弯。

前进目标上限为直道150、普通弯120、紧弯100，且不超过在线cruise。实际desired是“在线上限、弯道上限、起步包络”的最小值。

5ms下降最多1.25cm/s（250cm/s²）；150→120目标过渡120ms，150→100为200ms。出弯恢复上升最多0.5cm/s（100cm/s²），100→150为500ms。它们是目标变化时间，实际速度还受PID/电机/摩擦影响。

已在弯中时需同时满足：视觉需求≤45deg/s、|err|≤12、|控制gyro|≤40deg/s，最近帧年龄≤100ms，连续200ms，才清弯级恢复直道。条件中断就重置稳定计时。此设计使“图像看似回正但车身仍转”时不马上加速。

没有新鲜图像会暂停加速及稳定退出计时，但保持已有视觉命令、已有限速状态；不是摄像头断帧自动停车机制。图像持续LOST的停车条件则由app另行处理。

这个判断使用视觉控制需求，未做独立几何曲率拟合；kp1/kp2/kd/前瞻/缺行放大会共同影响弯级。此版本只降低vx，没有将omega/vy或四轮目标整体等比例缩小。

## 10. IMU怎样参与5ms控制

`imu_init()` 基础驱动最多重试3次；配置陀螺低通CONFIG=3、采样分频DIV=4，与200Hz一致，读回芯片ID/配置。稳定100ms后300次、每次间隔5ms校准，采样约1.5s，整个初始化比1.5s更长，WiFi时间另算。

计算三轴gyro均值零偏、方差以及平均重力；模长需0.75～1.25g，各轴标准差≤3deg/s。不满足分别返回错误，禁止正常发车。

每拍 `imu_update()` 读取acc/gyro并做两条路径：

- 姿态路径：固定三轴零偏→角速度deg/s，加速度g→四元数融合→roll/pitch/yaw。重力模长0.8～1.2g才作重力方向纠正；加速度没有绝对yaw观测。DWT计真实dt/迟采样，过长间隔不用陈旧角速度长时间积分。
- 控制路径：Z轴原始值减停车跟踪零偏→deg/s→安装符号-1→低通alpha=0.5。停车时零偏跟踪时间尺度约0.8s；K1后关闭动态零偏跟踪。

IMU倒装使上位机传感器坐标gz左转负右转正；控制归一化后左正右负。上传gz沿用固定三轴校准，并未作这个安装反号/控制低通，所以两者不是简单逐点完全相反。

`control_tick_isr()`：

```c
gyro_z_dbg=imu_get_gyro_z_dps();
omega_dbg=vision_omega_command-ctl_gyro_kd*gyro_z_dbg;
omega_dbg=clamp(omega_dbg,-ctl_omega_max,+ctl_omega_max);
vy_dbg=vision_vy_command;
```

gyro_kd=0.30，omega上限±240deg/s。例如视觉要求0而车身还左转150deg/s，则要求-45deg/s右转以抵消残余转动。

它是角速度阻尼，不是yaw角闭环，也不是完整的 `PID(omega_target-gyro)` 内环；当前roll/pitch/yaw主要用于显示，姿态角不直接进入四轮分配。持续转弯也会被阻尼削弱，不只出弯生效。

## 11. mecanum_inverse：车体三个需求变四轮目标

`motor.c:124`，全车符号x前、y左、omega左转；FL/RR滚子轴线\\，FR/RL轴线/。

完整轴距L=20cm、轮距W=18cm，等效系数 `(L+W)/2=19cm`：

```c
rot = omega*(pi/180)*19;  // cm/s，约0.331613*omega
FL = vx-vy-rot;
FR = vx+vy+rot;
RL = vx+vy-rot;
RR = vx-vy+rot;
```

代码先mm转m、deg/s转rad/s，最后转cm/s；MECANUM_Y_SIGN/W_SIGN当前+1，整体符号修正可在此完成。

前进分量四轮同号；向左横移FL/RR减、FR/RL加；左转左侧FL/RL减、右侧FR/RR加。三者线性叠加。目标允许负值，表示相应轮反转；没有运动学统一轮速限幅/饱和重分配，最终占空比饱和也可能破坏理想比例。

`control_tick_isr()` 将out[i]写到 `Motor_PID[i].Target`。`mecanum_drive/spin` 仅是便捷封装，正常路径调用完整inverse。轮径/电机68:16齿比不在inverse里再乘，因为输出本来就是轮周线速度；周长/编码器齿比由反馈换算处理。

## 12. 编码器：5ms计数变Actual

`encoder.c:72` 每拍读16位自由计数器，不运行期反复清零。`encoder_counter_delta()` 用模65536差分恢复正负方向；相邻拍净变化必须<32768，避免歧义。修正方向后保存瞬时脉冲，累积total/raw_total/absolute_total，并记录饱和标记和sample_count。

逐飞驱动实际 `kQTMR_PriSrcRiseEdgeSecDir`：A上升沿计数，B判方向，是1倍频。无每脉冲CPU中断，QTIMER硬件计数、PIT读取。

当前轮周长19.5cm、编码器1024线、轮侧68齿直接啮合编码器30齿：

```text
counts_per_cm = 1024 * 1 * (68/30) / 19.5 = 119.02906
Actual_cm_s   = corrected_delta / (0.005 * 119.02906)
```

5ms中1个计数约1.68026cm/s，80个约134.42096cm/s。这里没有再乘68/16电机传动比；`CHASSIS_GEAR_RATIO=4.25`当前只是定义，控制代码没有引用它。

| 轮 | 编码器A/B | 方向取反 | 电机DIR/PWM | 电机方向取反 |
|---|---|---|---|---|
| FL | C2/C24 | 1 | C9/C8 | 0 |
| FR | C0/C1 | 0 | C7/C6 | 1 |
| RL | C3/C4 | 1 | D2/D3 | 0 |
| RR | C5/C25 | 0 | C10/C11 | 0 |

电机/编码器修正解决不同硬件问题，目的是轮子向车前运动时Target与Actual均正，不能互相替代。

轮速没有额外滑动平均，直接本拍delta乘预计算系数。`distance_cm`累加四轮速度平均×dt，理想无滑移时是前进里程估计；不在当前循迹控制律中使用，也不是实际轨迹长度/横移测量。

K1清distance，但不清enc.total累计计数；CSV enc是上电累计计数，不是cm，也不是本次5ms增量。`encoder_snapshot()`短临界区复制计数；`encoder_set_counts_per_cm()`是校准接口，不在23项在线参数列表内。

## 13. 四个增量式速度PID

`Speed_PID_Crtl()` 先刷新Actual；开关关闭则停电机，开关打开逐轮执行 `PID_INC_Update()`→`motor_set_wheel()`。

当前FL/FR/RL/RR的Kp为0.22/0.20/0.18/0.20，Ki均0.001，Kd均0，Kff为0，因此实际是四个增量式PI：

```c
e0=Target-Actual;
delta=Kp*(e0-e1)+Ki*e0+Kd*(e0-2*e1+e2);
Out=clamp(Out+delta,OutMin,OutMax);
OutCmd=Out;
e2=e1; e1=e0;
```

误差变大P增加输出，误差变小P减少输出；持续误差通过每5ms的Ki累加。增量式的P乘的是误差变化，但不能因此认为它不具备普通比例作用；从复位累计展开，P对应当前误差贡献。Ki已经是离散每拍系数，没有再乘0.005；改环周期需重新考虑Ki/Kd。

单次delta限幅字段 `OutDeltaMax` 初始化为0，当前没有启用所谓“打滑增量保护”。输出Out与OutCmd限制±100%。如果开Kff，只在Target>Actual时额外加Kff*(Target-Actual)，这不是按目标速度标定的独立前馈；当前0不生效。

减速时Actual>Target会降低输出，可能降为负PWM主动反向；K2却是直接零PWM，不保留速度闭环制动。在线同步增益不重置Out/history，发车/停车才复位；速度闭环关闭的编译分支只按Target*0.10映射、限制±20%，当前不运行。

四轮相同速度目标不要求相同占空比：各轮负载、摩擦、电机差异由各自反馈补偿。它们不知道视觉误差、弯道类型或陀螺角度。

## 14. motor_set_wheel：PID输出变物理信号

PID浮点OutCmd先转int16，向0截断。18.9→18%、-18.9→-18%；PID内部仍保留小数累计值。当前最小占空比步进是1%，不是0.1%。

`motor_set_wheel()`：索引校验→安装取反→±100限幅→正负设置DIR→绝对值换成库PWM尺度。逐飞 `PWM_DUTY_MAX=10000`，因此18%写1800，100%写10000。

正逻辑占空比表示向车前转，FR安装取反后其DIR电平与其他轮不同；不是所有正目标都要求DIR高。PWM硬件17kHz持续输出，CPU每5ms修改占空比。

DRV8701E按DIR/PWM和动力电源驱动电机产生转矩→轮子改变转速→编码器更新→下一拍再纠正。占空比是驱动比例，不是电机端电压精确测量；实际轮速也不是简单固定线性比例。

`motor_stop()`调用四轮0，当前实现仍重写DIR为逻辑零分支对应电平；头文件“DIR保持”注释不精确。但PWM=0这个行为明确。

## 15. 同一个数值例子贯穿全过程

以下是假设某一拍的演算，不是本次实车测量。已经确认普通弯且vx规划达到120；加权后err=+40、上次死区后err=+30、控制归一化/低通后的gyro=-60deg/s。

```text
视觉线性项 = 1.60*40 = 64
视觉二次项 = .012*40*40 = 19.2
视觉D项    = .30*(40-30) = 3
omega_vis  = -(64+19.2+3) = -86.2deg/s
vy         = -.10*40 = -4cm/s
omega      = -86.2-.30*(-60) = -68.2deg/s
rot        = -68.2*pi/180*19 = -22.61598cm/s
```

| 轮 | 目标公式 | 目标cm/s |
|---|---|---:|
| FL | 120-(-4)-(-22.61598) | 146.61598 |
| FR | 120+(-4)+(-22.61598) | 93.38402 |
| RL | 120+(-4)-(-22.61598) | 138.61598 |
| RR | 120-(-4)+(-22.61598) | 101.38402 |

左侧比右侧快使车右转，对角差形成向右横移。若FL本拍修正计数80，则Actual=134.42096、e0=12.19502。再假设FL上次e1=8、Out=18%，则：

```text
delta=.22*(12.19502-8)+.001*12.19502=.93510
Out=18+.93510=18.93510%
下发=(int16)18.93510=18%，PWM库值1800
```

其他三轮必须用各自Actual/history/Kp演算，不能仅凭目标速度推导它们PWM。

## 16. 停车事件如何截断控制

`app_vision_poll()`每个新图像获得事件后：运行中斑马线上升沿累积到2次停车(reason1)；连续3帧LOST停车(reason2)；正常帧清lost计数。斑马线分支也清lost；停车/发车清相应运行计数。

`control_stall_watchdog()`同样按新图像调用：vx≥60、四个实际速度绝对值均<25，连续15帧停车(reason4)。50Hz时约0.3s，实际按处理帧数，不是独立固定300ms；单轮卡住但另一个仍≥25不会触发此“全轮慢”判据。K2 reason3。停车后 `control_update()`清视觉命令，下一拍控制tick不产生目标。

这些保护不会把当前车变成“自动启动”；只有K1可以从IDLE启动。画面断帧、WiFi断连本身没有额外直接停车动作，不能把它们等同LOST。

## 17. 上位机是观察/改参旁路

`wifi_poll()`每50ms复制IMU、编码器累计、四轮Target/Actual/已下发duty、err/omega/vx/vy、视觉和通信耗时生成148字节内层包。编码器/速度/IMU各自的快照内部一致，但不同快照之间不是整个系统的一次全局原子锁存。

| 内层偏移 | 数据 |
|---:|---|
| 0～35 | roll/pitch/yaw、gx/gy/gz、ax/ay/az，各float32 |
| 36～51 | 四轮累计enc，int32 |
| 52～59 | 编码器sample_count、参数seq，各uint32 |
| 60～75 | 四轮Target，float32 |
| 76～91 | 四轮Actual，float32 |
| 92～107 | 四轮整数下发占空比，转float32保存 |
| 108～123 | err、omega、vx、vy |
| 124～147 | vis耗时、间隔、帧数、WiFi服务本次/峰值耗时、视觉event，各uint32 |

序号缺号可能来自候选替换、失败或UDP丢包，不能仅靠seq判定控制中断漏拍。

图像内层是22560灰度+480逐行坐标/补线标记+12元数据=23052字节，1400字节每片，共17片，CRC覆盖完整帧。metadata来自真实取值行/拐点；PC画青边、黄中线、紫补线、候选/确认标记、全宽绿线，顶底20行不显示线条只影响显示，不改变控制计算。

上传启动间隔66ms；前一图像在途则继续处理新视觉，只保留后续候选，不创建无限图像队列。每次只提交一个异步SPI事务，图像最多连发4片或20ms批次后让参数，日志有发送优先级；接收指令也在事务间安排。eDMA负责SPI搬运，主循环推进状态机；仍有快照/CRC/协议处理CPU成本，不能说上传完全不占时间。

默认单端口固定8081，外层8字节MUDP：魔数、版本、type、payload长度；type1参数、2文字、3图像，PC解包后分到各显示区。兼容工程三端口不加此外层。控制算法相同。

在线参数MCAR GET/SET经模块6666接收。`control_param_set()`校验名称/有限范围、整数/步进，在短临界区修改变量并同步四輪增益；preview同步asc_far。ramp100～2000ms且5ms倍数，只能停车改；其他合法项可运行时改。共23项；弯道阈值/速度/加减速率不在当前在线表，需要改config重新编译。

参数只保存在RAM，重启恢复config默认。ALIVE只是确认上位机仍收到数据，不发车/停车。网络故障异步退避与恢复；彻底入网重试只停车执行，避免行驶主循环被同步入网等待占住。

| 弯道进入阈值 | 70/140 | 同一视觉需求何时确认降速 |
| 减/加速率 | 250/100 | 速度目标变化速率；不是实际车身加速度反馈闭环 |

判断回正慢先看err：err仍同号大，涉及图像/前瞻/视觉需求；omega已反号但gyro仍原方向，涉及实际转动和轮速响应；Target变化而Actual明显落后，再看各轮PID/duty；Target/Actual相近但仍甩尾，可能涉及打滑和几何/反馈标定，不能仅凭这组信号确认车身轨迹。
