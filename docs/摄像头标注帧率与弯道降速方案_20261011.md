# 摄像头标注、帧率改善与弯道降速方案（2026-10-11）

本轮已实施摄像头显示标注、上传协议和发送调度优化。**弯道降速部分是具体方案，尚未启用**；当前正常循迹仍以150cm/s为巡航目标，500ms起步斜坡、gyro_kd=0.30、lateral_gain=0.10及四轮速度环参数保持。

## 1. 摄像头显示改动

车端上传原始188×120灰度图与本帧处理结果；电脑绘制叠加层，不在发送前把灰度像素改成标记图。

| 显示内容 | 新样式 | 对应数据 |
|---|---|---|
| 左右边界 | 同一种蓝色 | g_vis.l_border/r_border |
| 中线 | 黄色 | g_vis.center_line |
| 补线/推断边界 | 左右统一紫色 | 原有repair_flags bit0/1 |
| 误差取值范围 | 两条横向绿色线，贯穿整幅图像宽度 | pho_center实际使用的y_far/y_near |
| 十字拐点/斜入十字的有效拐点 | 红色十字 | cross_detect计算的四个锚点；缺失侧不画 |

边界、中线、补线和拐点标记只在第20～99行显示，顶部0～19、底部100～119保留原始灰度。绿线是取值参照，按真实采样行绘制，不改变算法范围；若把在线preview_row调到20或100，取值范围会到10～30或90～110，参照绿线仍标出真实位置。

当前preview_row=55；pho_center使用55±10，即45～65行，**含两个端点，共21行**。在线调整前瞻后，绿线随下一张实际处理帧移动，不根据上位机输入框猜测。字体提示也显示本帧范围、拐点数量及候选/确认/短暂保持状态；暂停时对应冻结画面。

标记的是现有十字检测使用的拐点，不新增普通弯道拐点识别算法。没有有效拐点时不人为造点；没有执行本帧十字检测时，不把旧静态坐标叠到新图上。补线仍用紫色，左右真实边界才统一蓝色。

为了携带准确范围和拐点，新增MCAM v1的format=3：灰度22560字节、逐行坐标480字节、标注12字节，总长23052字节；仍17片，每片最多1400字节，末片652字节，CRC覆盖全部负载。上位机继续接收旧format=1/2；旧协议没有范围/拐点，显示升级提示，不伪造绿线或拐点。需要本轮固件与新版上位机配合。

## 2. 为什么提高“总控制频率”不能直接提高图像帧率

不存在一个统一的总频率，各任务按不同条件执行：

| 任务 | 当前周期/触发方式 | 与上位机画面的关系 |
|---|---|---|
| IMU、编码器、四轮速度环、运动学分配 | PIT_CH0，5ms，200Hz | 保证车辆闭环，不产生更多相机帧 |
| 按键识别 | PIT_CH1，10ms，100Hz | 主循环消费事件，负责K1/K2动作 |
| 相机采集 | 配置约50fps | 形成新图像，不等于上传速度 |
| 视觉处理/视觉外环 | 主循环只处理新帧，约20ms一帧 | CSV中的vis_interval_us反映实际处理间隔 |
| 数据上传 | 50ms目标，20Hz | 可与图像分别调度 |
| 图像上传 | 原100ms；本轮66ms，约15fps启动目标 | 真正约束画面更新频率 |
| SPI异步状态机 | 主循环每圈推进 | 轮询慢会把每片事务等待累积放大 |

RT1064的Cortex-M7最高600MHz，有较强处理能力，但“主频更高”不消除主动延时、模块等待和分包数量。[NXP官方规格](https://www.nxp.com/products/i.MX-RT1064)。

188×120一帧需要17个UDP包，每片SPI提交后现有驱动等待模块自动提交窗口约3ms（模块2ms，额外1ms余量）。仅此就超过51ms，还需SPI搬运、参数/日志端口切换、收到指令时的处理及视觉任务。因此这个协议目前难以把50fps全分辨率图像全部传到电脑；CPU算得更快也绕不过事务等待。

本轮修改config.h：

```c
#define APP_MAIN_LOOP_DELAY_MS (0u) // 去掉主循环每圈1ms强制等待
#define WIFI_IMAGE_PERIOD_MS   (66) // 约15fps上传启动目标
```

5ms速度/IMU、10ms按键、相机约50fps均保持；不增加重复视觉运算。驱动继续EDMA非阻塞，不缩短未经实测的模块3ms保护窗口，不修改WiFi模块固件。提高主循环服务频率可以帮助提高传输效率，这部分已执行。

直接把速度环200Hz提高到400Hz还需要重新评估ICM20602的数据输出率、滤波、编码器量化、内环执行时间和PID。当前Ki为每拍离散系数，周期减半而Ki不变会使单位时间积分作用翻倍；视觉D是每帧差分，视觉帧率变动也需重审。为解决上传问题无需引入这些控制变化。

## 3. 软件验证与实际边界

review_camera_poll_rate.py运行真实wifi.c及异步驱动，模拟40MHz SPI传输时长，每20ms占用1.5ms处理视觉，模块按2ms自动提交，保留3ms驱动等待。它将原调度与更密集主循环轮询分别执行5s：

| 软件模型 | 完整图像 | 参数包 | 参数最大间隔 |
|---|---:|---:|---:|
| 1ms主循环轮询、100ms上传间隔 | 8.6fps | 99包/5s | 79ms |
| 100us主循环轮询、66ms上传间隔 | 14.2fps | 100包/5s | 58ms |

两种情形均未出现空UDP包。100us是模型比较条件，实际程序删除主动等待，并没有新增100us定时器；实车轮询速度由任务、SPI中断和执行耗时决定。模型没有真实无线丢包、摄像头曝光变化或模块忙等待，**14.2fps不是实车已验证结果**。

实际C视觉/上传测试检查原始图与叠线同帧、快照在发送17片过程中不被覆盖、动态取值范围、缺失侧拐点、K2后图像/IMU仍发送、日志/失败恢复。电脑测试验证旧协议兼容、元数据校验/CRC、绿线、同色边界、拐点及上下20行隐藏。打包回环仅使用电脑18081/18082/18083测试端口，不连接实车。

烧录后看04页完整帧率，并同时保存CSV：vis_interval_us应仍接近20000us；比较vis_time_us、wifi_peak_us和NET错误。若上传频率提高但完整帧反而减少或CRC/超时明显增加，先将WIFI_IMAGE_PERIOD_MS恢复100，保留无主动延时的主循环。

## 4. 弯道降速的依据与可借鉴点

参考[Enterprise_E全向行进组开源项目](https://github.com/ittuann/Enterprise_E)及作者的[直道/弯道速度控制说明](https://ittuann.github.io/2021/08/28/CarElement.html)。仓库说明摄像头部分未开源，作者公开文章提出用远处有效中线判定加速条件，入弯减速、出弯加速。本方案借鉴这两个原则，以下数值是本车的待实测初始建议，并非照搬其标定参数。

同一转弯半径下，所需横向加速度约v²/R。从150降到100cm/s，理论需求成为原来的约44%；麦轮横向/纵向摩擦与普通轮不同，这只说明降低速度的方向合理，不构成具体摩擦系数或“不打滑”的保证。

当前视觉ω指令不按vx自动缩放。在ω保持不变时，R=v/ω随降速变小，a=vω从150到100只降低到约67%，同时转弯半径变小。不能承诺降速以后仍沿原来半径，也不应同时把ω按速度降低而削弱纠偏能力。第一轮只试速度规划，保持视觉/陀螺/横移增益，观察是否出现内切或摆动再决定后续调整。

## 5. 具体方案：提前看弯、平滑降速、确认出弯

### 5.1 输入和分工

保持固定preview_row=55及当前45～65行视觉转向窗口，不启用自适应前瞻。另取远处25～40行的有效中线，只用于预判降速，避免到大偏差才减速。至少8行左右真实边界均存在且center有效才采用该远窗；缺线、十字补线、斑马线不作为“已经是直道”的证据。

每张新图像计算远窗偏差e_far（px，可用去极值均值），换成同量纲的转向需求：

```text
omega_far = kp1*abs(e_far) + kp2*e_far*abs(e_far)   // deg/s，取绝对幅值
turn_need = max(abs(omega_vis), abs(omega_far))
```

omega_vis取视觉环原始命令，不能只用减过陀螺反馈后的omega_dbg，否则转动很快且陀螺正在反向制动时，可能误判需求很小。远窗不可用时只用本地视觉需求，但不允许凭远窗缺失加速；使用现有gyro_z控制坐标（左转正）检查出弯残余转动，不能直接把倒装传感器原始gz符号混进控制。

### 5.2 第一轮目标表

| 转向需求turn_need | 前进规划目标 | 解释 |
|---|---:|---|
| ≤35deg/s且稳定直道 | 150cm/s | 当前直道目标 |
| 35～100deg/s | 150→120cm/s线性降低 | 提前进入普通弯道减速 |
| 100～170deg/s | 120→100cm/s线性降低 | 紧弯继续减速 |
| ≥170deg/s | 100cm/s | 本轮暂定弯道最低目标，不代表所有急弯都能通过 |

35/100/170deg/s对应当前P项大致偏差18/46/68px，仅帮助理解，实际含视觉D，远近窗也不同，不能视为测量出的曲率阈值。如果提前减速不足，优先把35降低到25或把最低速度降到90；不要同时改视觉和四轮PID。

普通入弯需求连续两帧成立才升级减速（约40ms，实际按时间判断）；超过170deg/s可当帧减速。出弯要求turn_need<25deg/s、abs(本地err)<6px、abs(控制gyro_z)<30deg/s、图像有效，**连续200ms**成立，才释放至150。若任何条件反弹，立即取消出弯确认。减速和恢复阈值不相同，防止目标在直/弯状态之间跳变。

远窗不足8行或出现大面积补线时，禁止恢复高速并将规划上限暂收至100；现有连续出界/斑马线停车判据优先级更高，不能被降速策略替代。十字直穿可能因此变慢，属于第一轮保守取舍，应结合实际图像再区分元素。

### 5.3 每5ms平滑更新目标，全程保留纠偏

新图像只更新规划目标v_plan，PIT_CH0每5ms推进速度参考：

```text
减速率 = 250cm/s²  // 每5ms最多下降1.25cm/s
恢复加速率 = 100cm/s²  // 每5ms最多上升0.50cm/s
v_ref += clamp(v_plan-v_ref, -1.25, +0.50)
```

150→100目标约0.20s，出弯确认后100→150约0.50s。150→100减速阶段按理想目标平均125cm/s，需要约25cm提前量；摄像头25～40行究竟对应多远，需要实际标定，不能根据图像行号直接认定足够。实际轮速能否按0.2s降下来还由现有速度环/电源/机械惯性决定。

K1起步保留用户指定的0.5s斜坡：启动期v_goal=min(150×已运行时间/500ms, v_plan)，限速器的上升速率暂用300cm/s²，下降仍用250cm/s²；这样直道从0到150仍需0.5s，遇弯也可以减速。500ms之后v_goal=v_plan，上升速率切为100cm/s²。不能继续用固定启动比例覆盖规划结果，也不能把所有加速都改成100cm/s²而使K1起步变成1.5s。K2立即停止，不走减速斜坡。

gyro阻尼、视觉转向和横移每拍继续合成：

```text
omega = clamp(omega_vis - gyro_kd*gyro_z, -omega_max, +omega_max)
rot = 19cm * omega * pi/180
FL = v_ref - vy - rot       FR = v_ref + vy + rot
RL = v_ref + vy - rot       RR = v_ref - vy + rot
四轮各自按 Target-Actual 运行PID → 实际PWM
```

降低的是车体前进速度vx参考，不是四路占空比固定减一截，也不把所有轮速目标等比例缩小，否则转向/横移也随之削弱。弯道仍可能有外轮目标高于150，例如vx=100、vy=0、左转150deg/s时，rot≈49.7，左轮约50.3、右轮149.7cm/s。

## 6. 与实际代码的接入位置、参数管理和试跑判据

计划接入位置：

1. vision.c在pho_center之后输出远窗有效性/偏差；不改现有g_vis.err计算。
2. control_update每新帧更新v_plan、入/出弯状态及时间戳。
3. control_tick_isr把现在“启动斜坡乘ctl_speed_target”扩展为启动限制+速度规划限速器，然后照常陀螺反馈、mecanum_inverse和四轮PID。
4. control_state_launch/stop完整清理规划状态；停车优先。
5. config集中直道/普通弯/紧弯速度、需求阈值、恢复阈值、200ms确认、加减速率、远窗25/40和最低有效行8；下一版再接入06实时参数页及回执。
6. 遥测保留现有148字节前缀并追加v_plan、turn_need、e_far、valid_rows、curve_state和限速原因，便于区分“判弯太晚”“目标已降、轮速没跟上”“出弯过早恢复”。

第一轮保持gyro_kd=0.30、lateral_gain=0.10、视觉1.60/0.012/0.30、四轮Kp=0.20/0.20/0.18/0.18及Ki不变。看入弯前vx_cmd是否已下降、四轮speed是否跟踪目标，出弯后gyro转动是否消退，再释放速度。若仍外甩，先降低紧弯目标；若弯中内切、蛇行，检查远窗判定及转向与速度的匹配，不能直接加大横移；若出弯恢复太慢但姿态稳定，再缩短200ms确认或提高恢复加速率。

当前日志只能显示角速度和轮速，无法直接测车体实际横向滑移；“编码器轮速达标”不等于轮胎无打滑。需要结合画面/实车轨迹判断。已实施内容与未实施方案在本文件明确分开，后续启用后再写实测结果。
