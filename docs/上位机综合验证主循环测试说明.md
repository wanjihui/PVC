## 车端实际调用

`project/user/src/main.c` 的综合分支按下列顺序执行：

1. 时钟、UART1、全局中断准备。
2. `motor_init()`：四路DIR/PWM初始化，PWM=0。此分支以后不再调用电机函数，不执行速度PID。
3. `imu_test_init()`：ICM20602芯片、量程/采样寄存器、静止校准；失败则标记IMU无效，其余模块继续。
4. `encoder_test_init()`：初始化四路QTIMER和累计计数；方向修正仍为0、1、1、0。
5. `mt9v03x_init()`：总钻风初始化，最多3次尝试。失败则禁用图像上传，其余模块继续。
6. 启动5ms PIT_CH0，仅维护 `wifi_monitor_ticks`。不启动按键扫描定时器。
7. `wifi_spi_test_init()`：连接已有WiFi并配置电脑目标地址，成功后补发日志；失败后进入主循环，等待5秒再重试。

循环中的 `monitor_sample_poll()` 到期读一次编码器，并在IMU有效时调用 `imu_test_update()`。编码器读当前硬件计数、累计增量，IMU读取三轴加速度/角速度并解算roll、pitch、yaw。两者都在主循环上下文，PIT不再采样。

主循环取传感器快照，按50ms目标发送60字节参数。相机保持CSI/DMA后台采集，CSI中断由库维护完成帧标志；主循环检查 `mt9v03x_finish_flag`，按500ms目标复制图像快照、计算CRC并发送17个MCAM分片。相机数据采集仍依赖硬件中断，图像处理和上传在主循环，不做视觉循迹算法。

网络分包及socket操作之间也会协作调用采样函数，只访问IMU的SPI4和编码器QTIMER，不重入WiFi的SPI1。同步WiFi函数可能阻塞，5ms是目标而非固定保证，漏掉的历史IMU样本不能事后补读。此模式适合联调；正常循迹仍保留原来的PIT内环。

每秒向日志缓存写一条 `STATUS MAINLOOP`，并向上位机发送待发日志。WiFi失败重试本身会等待，期间主循环采样也可能推迟。

## 初始化日志怎么看

先在上位机开始三路监听，再复位车端，启动日志才有接收程序可收。下面是日志标签说明，不是本次实车结果：

| 模块 | 日志标签 | 能确认的内容 |
|---|---|---|
| 电机 | `[INIT] MOTOR CONFIGURED PWM=0` | 主控GPIO/PWM配置函数返回；没有驱动存在或接线检测，不代表再次实测旋转 |
| 编码器 | `[INIT] ENCODER CONFIGURED` | 四路QTIMER配置完成；须手转轮子看计数，无法靠初始化判断编码器是否接通 |
| IMU | `[INIT] IMU OK` 或 `[ERR][INIT] IMU FAIL stage=...` | 芯片响应、寄存器和校准检查结果；1芯片失败，2加速度异常，3校准期间运动，4寄存器配置异常 |
| 摄像头 | `[INIT] CAMERA OK` 或 `[ERR][INIT] CAMERA FAIL` | 相机配置返回结果；有完整图像到达才能证明采集和传输链条运行 |
| WiFi | `[INIT] WIFI OK` 或 `[ERR][INIT] WIFI FAIL stage=...` | 1模块/SPI通信失败，2入网失败，3UDP配置失败，4SSID为空或凭据长度超限；OK不等于电脑已收到UDP |

应用层日志同时写UART1和8KB缓存，入网成功后通过8082补发。缓存满时保留旧启动日志，丢弃新文字并统计 `log_drop_bytes`。WiFi尚未连上时，电脑不能即时看到其失败日志；后续连接成功才能补发，始终失败需用UART检查。上位机的时间戳是电脑收到日志的时间，启动补发文字可能集中显示同一时段。

`STATUS MAINLOOP`：

| 字段 | 含义 |
|---|---|
| `samples` | 编码器实际采样次数；不是UDP收包次数 |
| `enc` | FL、FR、RL、RR四轮累计计数，尚非cm/s |
| `imu/camera/wifi` | 对应初始化是否成功；不保证模块此刻仍在线或UDP送达 |
| `tx_fail/image_fail` | 参数或图像发送函数返回失败的累计次数 |
| `log_previous` | 上一次周期日志发送结果，0为模块侧发送流程成功 |
| `log_drop_bytes` | 车端日志截断或缓存满丢弃的字节数 |
| `imu_late/max_imu_us` | IMU实际更新间隔超过目标1.5倍的次数、最长单次采集/解算耗时（微秒） |
| `gap_ms/max_gap_ms/sample_late` | 最近采样间隔、最大间隔、超过5ms目标的累计次数；以5ms tick计时，包含启动入网和重连等待 |

## 电脑端操作

1. 使用桌面“Mcar WiFi 调试台”快捷方式。只让一个程序监听这组三端口。
2. 01调参：选“综合验证（IMU + 编码器）”，监听地址 `0.0.0.0`，参数8081、日志8082、图像8083，点击“开始监听（三路）”。
3. 在Keil打开 `project/mdk/rt1064.uvprojx`，选择 `nor_sdram_zf_dtcm`，编译并下载本次新程序。
4. 小车静置后复位，直到日志出现READY。初始化和WiFi等待期间也保持静止，避免影响校准与初始姿态。
5. 在01底部运行日志查看初始化结果与STATUS；02勾选参数曲线；03缓慢倾斜小车看飞机姿态；手转各轮看对应计数；04查看相机画面、遮挡镜头观察变化。电机不会主动转动。
6. 稳定运行后观察 `sample_late/imu_late` 的增长、图像未完整/超时/CRC错误、三路实际收包计数；保存日志和参数CSV，记录真实结果。

本次修改只需更新车端固件，上位机现有60字节解析、日志窗口和MCAM接收协议保持兼容。

## IP和端口的意义

当前车端目标电脑IP为 `192.168.50.117`，本次检查电脑连接 `ASC_Circuit` 且地址一致。IP指定哪台电脑；端口指定这台电脑里的接收入口。电脑监听 `0.0.0.0` 表示允许从本机所有网卡收包，它不是填给车端的目标地址。

| 端口 | 所在设备 | 内容和用途 |
|---|---|---|
| 8081 | 电脑 | 60字节二进制IMU/编码器参数，供字段解析、曲线与姿态模型 |
| 8082 | 电脑 | UTF-8调试文字，逐行放入运行日志 |
| 8083 | 电脑 | MCAM灰度图分片，组帧并校验CRC后显示 |
| 6666 | WiFi模块 | 模块本地socket端口，是发送数据的来源端口；电脑向模块发送指令时应填写模块真实IP和此端口，但本测试尚未定义执行控制命令 |

分端口是本项目的协议设计选择，不是WiFi或UDP规定必须如此。现有参数包没有类型头，若直接把文字或图像混进8081，浮点解析器无法可靠区分。分开后每个接收入口只处理自己的格式，还可独立统计、启停图像接收，保留原版角度协议。

也可以改为一个端口，在每个包里加类型、长度等统一包头，再由电脑分流处理；需要同时改车端和上位机协议。现在三端口仍共用一个WiFi模块、同一网络，模块单socket按批次切换目标端口，并非三条同时工作的连接。分端口本身不保证更快或可靠；UDP没有送达确认，以上位机实际收包和完整图像统计为准。
