## 结论与证据边界

不能仅凭参考仓库证明它实车从未断流。确认的事实是：它当前普通模式是固定一个UDP socket的标量遥测，不同时传原始相机图像、参数及独立日志；我们的单socket频繁切换8081/8082/8083，图像流量更大，SPI请求速率也更高。这些是负载、连接生命周期和时序条件的差异，值得优先排查，但还不能当作此次真实断流的唯一根因。

参考代码也存在没有累计事务超时、无法识别电脑实际接收、部分DMA错误按完成处理等缺口。因此应借鉴它的固定连接与简化发送路径，同时保留我们已有的事务期限和接收确认，不能认为完整复制其驱动就必然消除问题。

## 1. 实际启用的路径，而非文件夹中所有模块

`project/code/Protocols/wifi/wifi_cmd/wifi_cmd.h:35` 默认 `WIFI_IMAGE_ENABLE=0U`，IAR Core0工程所有CCDefines中均没有覆盖它。`wifi_cmd_Init()`（wifi_cmd.c:247）调用逐飞初始化后，仅建立一次固定UDP连接，远端端口1347，本地6666。普通运行没有在日志与遥测之间重建socket。

`main_cm7_0.c:1190` 主循环先消费最多100个到期的1kHz任务，再运行 `wifi_cmd_Poll()`；低频任务只在没有快速任务积压时执行。不能据此声称WiFi始终零阻塞：guard达到100时仍可能有快速任务积压，WiFi函数里也仍有等待调用。

当前 `core0_run_fast_loop_step()`（main_cm7_0.c:917）调用 `car_plan_debug_200hz()`；其周期5ms、用户变量63个。变量包含相机识别得到的信标/车灯坐标、规划及姿态标量，不是188×120整幅原始灰度。不要因为它也处理相机信息就视为与我们的图像发送负载相同。

完整调用链：

```
到期快速任务 → car_plan_debug_200hz → wifi_justfloat_Array
→ 打包时间戳+63个float+帧尾 → 256帧软件队列
→ wifi_justfloat_Poll → wifi_cmd_SendBuffer
→ wifi_spi_send_buffer（复制到驱动并置BUSY）
→ 主循环wifi_cmd_Poll → wifi_spi_send_poll
→ 数据载荷发送 → 检查应答 → 释放BUSY → UDP显式flush
```

图像模式不与上述遥测同时工作：`wifi_cmd_Init()` 的图像分支改连TCP，`wifi_justfloat_Array/Poll()` 在图像模式直接返回，主循环也跳过普通 `wifi_cmd_Poll()`。`wifi_image_SendFrame()` 在project中只找到定义，没有实际调用点；因此不能拿它证明当前分支已经实测“持续相机图像和高频遥测并发”。参考文档 `docs/02-communication/wifi-spi-debugging.md:232` 同样说明图像与普通遥测模式互斥。

## 2. 固定socket与我们三端口切换的差别

我们的 `code/wifi/wifi.c` 为参数、日志、图像分别指定8081/8082/8083。底层模块只有一个当前socket，`wifi_spi_send_async()`（async.inc:124）遇到目标端口不同，实际进入：

```
CLOSE_SEND → CLOSE_REPLY → CONNECT_SEND → CONNECT_REPLY → DATA_SEND
```

这不是简单改一个电脑解析字段，而是关闭并重新建立模块连接。参数每秒约20包，夹在持续图像流中时，一包参数可能引起“图像→参数→图像”两次切换，实际可能达到每秒数十次；当前没有记录切换计数，不能报成已实测准确次数。低频日志还会增加切换。

现有图像最多连发4片或20ms后让出参数，减少了逐片切换，但没有消除上述机制。非阻塞化只让CPU不在原地等待，不能消除模块内部关闭、建连、清缓冲的开销。ALIVE/socket刷新是检测恢复措施，也没有去掉正常发送期间的频繁切换。

固定一个目标端口并用应用层类型区分参数/文本/图像，更接近参考代码的连接生命周期。电脑依然可以分三个窗口显示，不需要在无线模块端也建立三个目标连接。本轮没有执行该协议迁移。

## 3. 数据量与SPI速率

参考当前活跃遥测：63个用户float，加1个时间戳和4字节帧尾，大小 `4×(63+1)+4=260` 字节。5ms周期对应理想52,000B/s，不含UDP/IP/WiFi开销；这是生成目标，不等于已证明长期实际吞吐。

我们的格式3相机载荷：22560字节灰度、480字节边界/中线/补线、12字节元数据，共23052字节。17个分片各加24字节头，总23460字节/帧。15fps目标约351,900B/s；若8fps则187,680B/s，再加20Hz的148字节参数约2960B/s及日志。相机上传已明显改变压力条件。

参考SPI配置请求10MHz，我们请求40MHz。实际速率由硬件分频决定，本轮未用仪器测量。40MHz没有直接违反之前查到的模块40Mbps上限，但最高允许速率不等于所有排线、供电、时序组合都稳定。相同WiFi模块也不代表两个主板的SPI时序和信号条件相同。

若进行单变量验证，可先只把SPI请求速率降到10MHz，保持协议/图像间隔/车辆控制不变，做停车连续收发对照。只发送260字节时10MHz载荷理论约208μs，我们1424字节分片在10MHz约1.14ms（均未计握手/中断/主循环），对比不能只看SPI时钟数字。本轮没有改速率。

## 4. “用了DMA”需要看真正命中的分支

参考 `wifi_spi_tx_dma_start()`（zf_device_wifi_spi.c:189）有 `len>256u` 直接失败的限制；`wifi_spi_send_poll()`（:793）遇到DMA启动失败便使用 `spi_write_8bit_array()` 同步发送载荷。因此当前260字节遥测实际上全部越过DMA长度限制，走同步回退；少通道、≤256字节遥测才命中该DMA路径。

正常DMA路径先清头部RX FIFO，TX DMA期间不断清RX FIFO，DMA完成后再等 `Cy_SCB_IsTxComplete()`，确认最后SPI位已经移出才拉高CS。这个末位完成检查值得学习，DMA完成不自动等于物理总线完成。同步回退路径又依赖原SPI写函数的完成语义。

我们的RT1064实现使用SDK配对TX/RX eDMA，接收侧持续搬运，SDK以接收传输完成触发回调拉高CS；数组及SDK DMA句柄位于非缓存SDRAM。不能复制CYT4BB7 PDMA寄存器、通道和缓存布局。更应该核对实际CS/INT/SCK/MISO时序，而不是仅因为它的结构简短就推定它更可靠。

## 5. 队列和接收调度

参考JustFloat队列256帧、最大单帧408字节，满时拒绝新帧；同一个1ms tick只接受第一份成功入队数据，正在发文字时暂停普通遥测。它适合吸收短暂延迟，但持续生产超出发送能力仍会满。队列在提交驱动成功后立即出队，而非SPI/UDP/电脑接收成功后，因此没有端到端保交付保证。

我们参数只保存最新候选，以避免上位机显示积压的旧轮速；图像只有当前不可变快照，日志缓存8192字节。这种差别会影响历史曲线完整性，不能把256帧队列当作永久断流的解决办法。

参考飞行状态 `wifi_cmd_Poll()`（wifi_cmd.c:302）只推进发送、flush与JustFloat，随后返回，不主动读取和解析文本命令。待机才调用原同步 `wifi_spi_read_buffer()`，它可能等待模块。我们还支持运行期在线调参、接收确认，空闲事务之间每10ms做异步接收读，调度与交互压力又不同。

## 6. 它也没有永不断流的防护

源码确认的边界：

- `WAIT_SEND` 的 `wifi_spi_wait_idle(1)` 超时只是本次返回，下次继续同一状态；没有累计200/500ms期限。
- `SEND_DMA_WAIT` 在DMA一直没有完成标志时一直返回，BUSY和CS低可能一直保留。
- `SEND_TX_WAIT` 等最后SPI位完成也没有累计期限。
- `DRAIN_REPLY` 对非终止应答不会释放BUSY，没有总事务期限。
- `wifi_spi_tx_dma_is_done()`（:275）遇到非COMPLETION DMA cause同样返回完成，未向上层区别报告错误。
- `s_wifi_cmd_ready` 主要记录上电初始化成功，常规运行没有电脑接收确认和自动离线/重新入网逻辑；UDP没有应用层ACK。
- 普通UDP `FlushNow()` 仍同步调用原 `udp_send_now()`；文字回包还会循环推进最多20000次等待发送完成。它并非整个运行路径严格无等待。
- 模块2ms自动发UDP的机制也适用它。它使用显式flush，若flush被推迟超过自动发送窗口，也存在空包风险；本轮没有用真实模块证明参考项目是否发生过这种情况。不能直接把该显式flush加回我们已经修正的路径。

参考自述也强调UDP会丢帧、队列会满、飞行中热拔模块未做功能保证；不能将没有公开失败日志解释为已经验证所有故障恢复。

## 7. 本轮检查与优先级

`tools/review_reference_wifi.py` 直接提取参考文件中的真实 `wifi_spi_tx_dma_start/send_buffer/send_poll` 编译运行，其余SDK/GPIO/应答为模拟：

1. 260字节实际进入同步回退，148字节进入DMA分支。
2. INT持续不就绪，连续1000次poll仍保留WAIT_SEND/BUSY。
3. DMA持续不完成，连续1000次poll仍保留SEND_DMA_WAIT/BUSY及低CS。
4. 持续返回未知应答，连续1000次poll仍保留DRAIN_REPLY/BUSY。

全部断言通过。测试说明代码的分支与故障响应，不代表参考飞机实测发生上述故障；模拟次数也不是实测毫秒时长。

后续优先建议：

1. **先验证固定单socket发送。** 参数/日志/图像通过类型封装共用一个UDP端口，保留电脑三个展示区，减少正常期模块关闭/建连。涉及车端与上位机同时改协议，须保持旧协议兼容。
2. **分开做负载和速率对照。** 例如只参数、参数加低帧率图像、再恢复目标帧率；SPI10MHz对照40MHz应另做一轮，不同时改变所有因素。停车连续运行可复现此前停车断流，更便于诊断。
3. **保留事务超时、DMA中止及ALIVE。** 新增socket切换计数、阶段/结果、确认年龄，与电脑各路接收差分对照；ALIVE只证明模块近期至少一路有进展，不能检测“图像单独断、参数仍正常”的每路问题。
4. **进一步区分模块下行与上行。** 记录超时阶段、INT电平、SPI协议应答；必要时测CS/INT/SCK。这样才能区分socket生命周期、模块忙、DMA卡住、无线丢包或电脑接收问题。

这些建议在本次审查中尚未执行，当前下载程序仍是上一轮版本；不改变150cm/s、45行前瞻、速度PID和K1/K2控制。
