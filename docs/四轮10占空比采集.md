# 四轮10%占空比与编码器WiFi采集（历史版本）

2026-10-07已切换为[四轮独立速度环调试](四轮独立速度环调试.md)：当前K1启动四轮150cm/s目标闭环，主循环统一调用app_poll。以下保留之前10%落地采集的说明，不代表当前固件行为。

## 烧录后的行为

上电将电机PWM初始化为0。电机、编码器、按键与WiFi初始化完成后等待K1；K1使四轮各输出10%，K2立即清零。同时识别到K1和K2时，以K2停车为准。

上电及停车期间不发送UDP参数、图像或日志。K1后允许发送，K2本圈先清PWM、再停止发送，再按K1恢复。WiFi保持连接，编码器仍按5ms采样；启动/停车日志等下一次K1后补发。启停日志中的ms为板上采样计时，用于区分缓存补发的事件时间和电脑收到日志的时间。已经提交的UDP包或上位机排队数据可能在停车后才显示。

`project/user/src/main.c`的测试循环注释`app_poll()`，直接写四次独立调用：

```c
motor_set_wheel(WHEEL_FL, running ? 10 : 0);
motor_set_wheel(WHEEL_FR, running ? 10 : 0);
motor_set_wheel(WHEEL_RL, running ? 10 : 0);
motor_set_wheel(WHEEL_RR, running ? 10 : 0);
```

随后调用`app_motor_test_poll(running)`，仅在running为1且WiFi已就绪时调度发送，循环延时5ms。真正编码器采样由PIT_CH0每5ms执行，PIT_CH1每10ms识别按键。测试不执行视觉转向或轮速PID，不初始化IMU和摄像头。相同占空比并不保证四轮实际速度相同。

## 上位机操作

1. 打开现有新版上位机，电脑连接项目已配置的WiFi网络。
2. 在调参页选择“综合验证（IMU＋编码器）”解析规则，参数端口8081、日志端口8082，开始监听。
3. 复位小车，先等待初始化完成；此时上位机没有新数据，启动信息可通过串口观察。
4. 按K1后四轮10%运行并开始传输，运行日志会补发`MCAR_FOUR_WHEEL_10PCT`、`CONFIGURED`、`WIFI OK`等启动记录。采集起转和稳定运行阶段，按K2停车并停止发送。CONFIGURED仅表示外设已配置，不表示芯片ID自检通过。
5. 保存全部解析数据的CSV，交给我分析。此次IMU未初始化，相关9个浮点字段为NaN；上位机会标记这些字段无效，编码器字段仍正常解析并保存。仅需编码器页面时，可以删除9个IMU解析字段，保留下面6项。图像页此次没有新图像。

参数沿用60字节小端`<9f4i2I>`协议，不需要重编译上位机：

| 字段 | 字节偏移 | 含义 |
|---|---|---|
| enc_FL / enc_FR / enc_RL / enc_RR | 36 / 40 / 44 / 48 | 四路方向修正后累计整数计数 |
| samples | 52 | 实际5ms采样次数 |
| seq | 56 | 数据包发送序号 |

发车期间参数目标50ms发送一次，即20Hz；编码器本地始终200Hz采样。使用累计值差与采样次数差恢复每个发送区间的平均轮速，避免把电脑收包抖动直接算作轮速变化。重新K1发车后跨越停车间隔的第一组差分应排除，避免将静止时间混入运行速度：

`轮速(cm/s) = Δ累计计数 / 119.02906 / (Δsamples × 0.005)`。

原始计数继续使用整数count；控制层速度使用cm/s、距离使用cm。网络发送不是编码器采样时钟。日志仍由`wifi_log()`缓存、入网后补发；UART1可作为备份。

## 参数与用途

L=20cm，W=18cm，车轮周长19.5cm；1024线正交编码器一倍频，68齿车轮轴带动30齿编码器轴，理论每厘米计数119.02906。电机方向补偿仍为0/1/0/0，编码器为0/1/1/0。

用户确认从车顶俯视、车头朝上：FL/RR滚子轴向为左上—右下，FR/RL为左下—右上，与现有逆运动学匹配。

四轮大约7%起转为用户观察值；当前统一10%用于取得有运动的响应数据。此数据能比较四轮方向、稳定速度和起转过程，并为速度环选初值；完整PID效果需要切入闭环后记录目标与实际响应来验证。
